# D23-D24: Lookups & deduplication + ICP scoring in Clay (2026-09-23)

## TL;DR

- Despite the session title mentioning "ICP scoring," this session's actual content is: cold-outbound messaging philosophy, Clay Lookups (single-record and multiple-record) for cross-table data sharing and blacklist/exclusion enforcement, deduplication done in Claude (not Clay) using a 3-parameter cascade, the "similar to" vs "contains" job-title filter (60% more coverage), language/geo/network-size/tenure filters for international and quality targeting, and an introduction to Sculptor (Clay's table-aware AI Q&A agent) and Live Tables (API-driven, headless Clay). Account-level scoring itself was covered the prior day (see D19-D20).
- Blacklist (permanent — competitors/companies building the same thing, never contact) is explicitly distinguished from Exclusion list (temporary — current clients/active CRM deals, don't re-approach); both are implemented in Clay via a Lookup against a reference table, filtered to "has no results" to get your clean, safe-to-contact set.
- Deduplication should NOT be done by a Clay dedupe-on-full-name feature — common names collide (many "Alex Johnson"s) and you'd wrongly strip real distinct people. Instead: export CSVs, upload to Claude, and dedupe using a 3-parameter cascade: (1) LinkedIn URL, (2) email, (3) full name + company name combined.
- "Similar to" job-title matching in Clay's people search returns materially more (and, per Yogesh, better) results than "contains" — up to ~60% more leads in the same search — because "contains" is a rigid substring filter that misses valid title variants.
- House rule: qualification signals should qualify roughly 60–70% of a 100-company list; if your signals are knocking that down to 20–30%, your parameters are too strict/vague and you're "ruining the data," not improving it.

## Key concepts

**Cold outbound messaging philosophy (context-setting, not Clay-specific).** Keep messaging warm even when technically cold: prioritize reaching people who are existing LinkedIn connections, have engaged with your content, are ex-colleagues, or have visited your website — over pure strangers. When reaching a genuine stranger, keep the message short and purpose-first; long/complex messages get ignored. Personal case studies/proof and small emotional hooks (referencing something specific and human) noticeably improve response. Regional insight: markets that receive fewer cold messages overall (Yogesh's example: the Netherlands) respond better to cold outreach simply because the channel isn't saturated there yet — and localizing language (sending Dutch-language messages to Dutch prospects) improves this further. Yogesh offered to share his own messaging document templates with the group informally (via WhatsApp/offline), not shown in the transcript.

**Clay Lookups — the mechanism for sharing data across tables/teammates without re-enriching.** Because multiple GTM engineers or teammates may work on the same underlying company/person data, "Lookup" columns let one table pull already-enriched fields from another table (or from a connected CRM object) by matching a key, instead of re-running paid enrichments. Two variants:
- **Lookup Single Record**: matches one row in the source table to the target column (e.g., match "Company" in Table B against "Company Name" in Table A) and pulls back one record's fields.
- **Lookup Multiple Rows**: matches and *counts/aggregates* across multiple rows in the source table — used, per Yogesh's example, to answer "how many of my 10,000 people work at these 1,000 companies?" without burning AI/Claygent credits; it's a formula-based join/count, not an AI call.
Lookups can also point at connected CRM objects (Yogesh demoed pointing at HubSpot's four object types — Companies, Contacts, Deals, and one more he didn't name) so a GTM engineer can, e.g., pull more contacts for a company straight from Clay without opening HubSpot at all — useful when a salesperson says "this account only has 5 people and none are answering, can you find more?"

**Blacklist vs Exclusion List — the precise operational distinction (important, often confused with generic "Do Not Contact" lists).**
- **Blacklist** = permanent, never contact. Contains direct competitors or companies building the same product/space (Yogesh's example: Razorpay and PhonePe are permanently blacklisted from ever cold-emailing each other; similarly Swiggy/Zomato, Cashfree/Razorpay, or CRM competitors like Zoho vs HubSpot). Rationale: getting caught reaching out to a direct competitor is a PR/trust risk that can visibly embarrass a company on LinkedIn, and Yogesh notes agencies have lost real clients this way.
- **Exclusion List** = temporary, contains current active clients and companies with an ongoing/won deal tracked in the CRM (HubSpot in the demo). Rationale: re-approaching someone you already have a live relationship with, cold, looks bad and damages the relationship — but it's not permanently forbidden the way a competitor is.
Several participants (Gagan, sampath) noted this maps onto the more familiar industry term "Do Not Contact (DNC) list," which they described as usually a blend of both categories; Yogesh's distinction is that DNC/exclusion is situational and reversible, while true blacklist is absolute and permanent.

**Implementing blacklist/exclusion checks via Lookup + filter.** Build (or import) a small reference table of blacklisted/excluded company names. On your main outreach table, add a Lookup Single Record against that reference table keyed on company name. Then filter that lookup column to "has no results" — this isolates exactly the companies that are safe to contact (i.e., not found on the blacklist/exclusion table). The same lookup-to-CRM pattern (pointing at HubSpot Deals) lets you build the exclusion check directly against live deal status rather than a static list.

**Why dedup should be done in Claude, not Clay's built-in name-based dedup.** Clay's dedupe-by-full-name is flagged as actively wrong for real-world use, because common names collide across unrelated people — Yogesh's example: many people worldwide are named "Alex Johnson"; naive full-name dedup would wrongly merge/remove genuinely distinct individuals. The safer cascade, done by exporting CSVs from Clay (Tools → Export → Download CSV, for both company and people sheets) and uploading them to Claude (any tier, free or paid) with a "combine and dedupe" instruction:
1. First pass: dedupe on LinkedIn URL (if two rows have different LinkedIn URLs, they are, by definition, different people — LinkedIn URL is unique per person).
2. Second pass: dedupe on email address (two different real emails = two different people).
3. Third pass: dedupe on the combination of Full Name + Company Name together (e.g., "sampath at Razorpay" is unique even if "sampath" alone is common — the combination is what makes it a safe key), never full name alone.
Yogesh's cost-efficiency framing: Claude ($20/month) doing this cleanup work is cheaper than relying on Clay ($120–190/month) to do everything, so "use less Clay wherever another tool can do it as well or better" is presented as a general operating principle, not just a dedup-specific tip.

**"Similar to" vs "Contains" in Clay's people-search job-title filter.** "Contains" is a rigid substring match — it only returns titles that literally contain your typed string. "Similar to" uses broader semantic/fuzzy matching and returns meaningfully more qualifying people for the same intended role — demoed going from a lower count to 99 results by switching the filter mode and removing an overly-narrow accompanying keyword (e.g., dropping "marketing" to isolate "sales," or vice versa, while debugging). Yogesh's stated rule of thumb: switching from "contains" to "similar to" can roughly double your lead coverage (~60% more leads for the same underlying search intent) — this is called out as a very common mistake ("this is a very big mistake people make nowadays") because "contains" silently narrows your addressable list without any obvious warning sign.

**Do qualification filtering upstream (in the data source) where the source tool already supports it, not entirely inside Clay.** sampath found that companies he'd already filtered for a specific attribute in Prospio (e.g., recently funded) were dropping out again when re-qualified inside Clay, shrinking his usable list unexpectedly. Yogesh's guidance: if the source data provider (Prospio/Apollo/Crossview) already offers that exact filter as a paid feature, use it there at extraction time rather than trying to re-derive the same qualification inside Clay — "clay's use should be minimal... we should use less Clay features as possible because everything outside Clay is growing" (i.e., competing data tools like Prospio are adding more of these native filters/validations, including MX-domain and email-validation features, so Clay increasingly should be reserved "for what other tools cannot do.")

**Warning about Clay's own underlying people-search data quality.** Yogesh flags — without demoing on-camera in this transcript — that Clay's raw people database contains significant self-reported noise (his example: searching for "CEO of Microsoft" on Clay surfaces many Indian LinkedIn profiles that merely list themselves as "CEO at Microsoft" without actually holding that role). His conclusion: Clay's own contact database is not generally the tool people rely on for final outreach-grade data — Apollo/Prospio-style dedicated data providers are considered higher quality for that purpose; Clay's strength is orchestration/enrichment/logic, not being the primary source-of-truth people database.

**Job-title language localization for non-English-speaking markets.** For markets like Germany, Spain, China, or Korea, searching only in English job-title terms (e.g., "founder") misses a large share of the real target population, because many LinkedIn profiles in those markets are written in the local language. Practical fix: search using the local-language equivalent term as well (Yogesh had the group Google-search the German and Spanish words for "founder" live, to make the point concretely) — apply this per-territory whenever operating outside English-first markets.

**Clay's native Language filter (people search).** Beyond job-title language, Clay has a standalone "Language" filter that detects the language a LinkedIn profile's name/content is associated with (demoed: German, Hindi, Telugu, attempted Odia and "Jewish"/Yiddish-adjacent, with mixed live results). Use case: when doing outbound as a founder with no existing network in a new market, a GTM engineer can find LinkedIn founders who speak the founder's own native/heritage language and add a small personalized P.S. line referencing the shared language/background — a lightweight warm-connection tactic distinct from the shared-employer/education tactic from D19-D20.

**Network-size / follower-count filter as a spam-profile screen.** Under "Network and reach," "Estimated audience size" = LinkedIn follower count; "Network size" = LinkedIn connection count. Setting a minimum threshold around 100 for both filters out low-activity or fake/junk profiles. Yogesh's live example: he opened a returned profile row (facetiously labeled "Narendra Modi" in the transcript) to show that a filtered search can still surface odd/unverifiable entries, and cautioned that a large share of what a naive search returns can be non-real "viewer" profiles rather than genuine account holders — reinforcing why the network-size filter matters as a basic quality gate.

**Tenure-in-current-role filter (buying authority proxy).** "Months in current role" (minimum threshold) filters out people who've only just joined a company. Rationale: someone one month into a new role typically has no real purchasing authority or context to approve a deal yet ("I cannot sell you something right now because you just joined one month back... why would they come in and say okay we need to purchase a tool of 1 crore rupees"). Yogesh's default suggestion was a 12-month minimum; Gagan pushed back based on his own experience that many companies use 6 months instead, especially where the buying committee/process is informal; Yogesh agreed 6 months is also a reasonable choice — the exact threshold is a strategy/business call, not a fixed rule, and Yogesh frames the ability to make that judgment call correctly as something that requires actual sales/marketing knowledge, not just Clay mechanics.

**Finding a LinkedIn URL when you only have email/name/company (a common real-world gap).** Any Clay people-enrichment feature (e.g., "Enrich Person") requires a LinkedIn URL as the join key — it cannot work from email alone. Fix: run a Claygent/"Use AI" column prompted to "find the LinkedIn URL of the person," mapping in Full Name, Job Title, and Company Name as inputs; once the URL column is populated, chain into "Enrich Person" as normal.

**Sculptor — Clay's built-in, table-aware AI Q&A agent.** Distinct from Claygent (which runs inside a specific enrichment column against the web) — Sculptor is a standalone chat-style AI agent that has visibility into your actual live table and can answer analytical questions about it directly (e.g., "does my Clay table look perfect?", "which rows are missing a state/region field?"). Important UI note demoed live: Sculptor offers a toggle between "Build" and "Analyze" — Yogesh explicitly warned to keep it on "Analyze," because "Build" mode will actually start building/modifying the table for you rather than just answering questions. Use case demoed: sampath had a list of startup founders (name, company, employee count, email) and wanted to check whether each founder is still at that company — Sculptor (after first getting LinkedIn URLs via the AI-lookup method above) is presented as the right tool to interrogate that table directly, "because Sculptor sees your table first, then answers" (i.e., it grounds its answer in the actual data rather than answering blind).

**Live Tables (mentioned/previewed, not built in this session).** Introduced only briefly at session close: a "Live Table" runs via Clay's API in the background without anyone needing the Clay UI open at all — described as the next topic to cover, not demonstrated here.

## Tools shown & how they were used

**Clay — Lookup Single Record (cross-table enrichment reuse).** On a secondary/reference table (e.g., one enriched separately with "company headquarters" via a Use-AI column), copy the company names into your main table (or vice versa) → Add column → Lookup → "Lookup Single Record" → select the source table → set target column match ("Company" contains/matches "Company Name") → Save and run 50 rows. Result: the reference table's already-computed fields (city, region, country, source URL/name) appear on your main table without re-running the enrichment. (00:06:09–00:15:46)

**Clay — Lookup Object (pointing at a connected CRM, e.g. HubSpot).** Add column → Lookup → "Lookup Object" → select the connected CRM app → choose one of its object types (Companies/Contacts/Deals/a fourth type not named in-session) → map the match field → this requires the CRM account to actually be connected in that Clay workspace (Gagan's HubSpot wasn't connected live in this demo, so Yogesh described rather than fully executed this one). (00:12:02–00:13:24)

**Clay — Lookup Multiple Rows (aggregate/count across many matches).** Add test rows to a scratch/reference sheet (demo pasted "Pando" [unclear exact name in transcript] repeatedly into rows 11–20) → on the main table, add column → Lookup → "Lookup Multiple Rows" → select the same source/target match → run → returns a count (demo returned "11 records" for the repeated test value) — explicitly framed as a formula-based way to answer "how many X are in Y" without spending Claygent credits on a search. (00:15:46–00:18:48)

**Clay — filtering a Lookup column to isolate the safe-to-contact list.** On the Lookup Single Record column → Filter → "has no results" → this removes any row that matched something in the blacklist/exclusion reference table, leaving only companies safe to contact. (00:20:13–00:21:27)

**Claude (chat/Claude Code) — dataset dedup and cleanup.** Export CSVs from Clay for both the company sheet and the people sheet (Tools → Export → Download CSV) → upload both files into a Claude conversation/Claude Code → give an explicit instruction (used verbatim in-session): "Combine and dedupe this file in this exact method" — where "this exact method" refers to the 3-parameter cascade (LinkedIn URL → Email → Full Name+Company Name) that Yogesh dictated in the same message — → Claude returns one cleaned, deduplicated, combined file. A follow-up prompt was also used to backfill seniority level from job title text directly inside Claude, as a second cleanup pass. (00:25:30–00:31:21)

**Clay — Job title match-mode toggle ("similar to" vs "contains").** On an existing "Find People" search's source/input configuration → Edit source → Edit inputs → Job Title field → toggle match mode from "Contains" to "Similar to" → observe result-count jump (demo went from a lower count to 99 after also removing an overly-narrow secondary keyword like "marketing" while isolating "sales"). (00:37:08–00:42:56)

**Clay — Language filter (people search).** New "Find People" search → Language filter → type a language (German, Hindi, Telugu tested; Odia and Yiddish/Jewish attempted with inconsistent live results) → returns profiles Clay associates with that language via name/content signals. (00:47:26–00:50:37)

**Clay — Network & Reach and Experience filters (quality/tenure gates).** Find People search → "Network and reach" section → set Estimated Audience Size (followers) and Network Size (connections) minimums, e.g. 100 → "Experience" section → "Months in current role" minimum, e.g. 6–12 → applied together as a standard quality/eligibility gate on any outbound list. (00:50:37–00:55:55)

**Clay — AI "Find LinkedIn URL" column (for email-only records).** Add column → Use AI → prompt: "Find the LinkedIn URL of the person," mapping Full Name + Job Title + Company Name as inputs → Generate → run → then chain into "Enrich Person" once the URL is populated. (00:56:29–01:00:31)

**Clay — Sculptor (table-aware AI agent).** From a sheet, open the Sculptor panel → set mode toggle to "Analyze" (not "Build," which would start modifying the table) → type any natural-language question about the table's contents or completeness (demo questions: "am I missing a value for state/region on row X?"; conceptually, "does my Clay table look perfect?"; sampath's real use case, "check if these founders are still at the same company") → Sculptor answers grounded in the actual current table data. (00:57:00–01:00:31)

## Clay build steps demonstrated (reproducible order)

1. Build (or import) a small blacklist/exclusion reference table of company names your client can never (blacklist) or currently shouldn't (exclusion) contact.
2. On the main outreach table, add a Lookup Single Record column matching Company against that reference table; filter the result to "has no results" to isolate the safe-to-contact set.
3. Where possible, also point a Lookup Object column at the client's connected CRM (e.g., HubSpot Deals) to catch active-deal exclusions dynamically rather than relying only on a static list.
4. Use Lookup Multiple Rows wherever you need a count/aggregate across a large people-to-company mapping — never spend a Claygent/AI credit on something that's really a join/count.
5. Before final delivery, export the company sheet and the people sheet as CSVs and run them through Claude with an explicit "combine and dedupe" instruction using the 3-parameter cascade: LinkedIn URL → Email → Full Name+Company Name (never full name alone).
6. Audit every people-search job-title filter: switch "contains" to "similar to" wherever coverage matters, and re-check result counts before/after.
7. For any non-English-market list, add the local-language equivalent of your core title keyword (e.g., "founder") alongside the English term, and consider Clay's Language filter for warm-connection personalization angles.
8. Apply Network & Reach minimums (~100 followers/connections) and a Months-in-current-role minimum (6–12, chosen per client's actual sales process) to every outbound people list as a baseline quality gate.
9. For any record missing a LinkedIn URL, run a Use-AI "Find the LinkedIn URL" column mapped on Full Name + Job Title + Company Name before attempting any person-level enrichment.
10. Use Sculptor in "Analyze" mode to interrogate a finished table for completeness/quality issues before shipping it, rather than manually scanning row by row.

## Instructor rules, opinions & decisions

- Keep outbound messaging short, purpose-first, and warm wherever a real connection point exists (shared LinkedIn network, past colleague, site visitor); never send long/complex cold messages.
- Localize messaging language and expect materially different response norms in markets that receive less cold-outreach volume than English-speaking/US markets.
- Blacklist = permanent, never contact (direct competitors / same-space builders); Exclusion list = temporary (current clients / active CRM deals). Treat these as structurally different lists, not one combined "DNC list," and always run a lookup-based check before any send.
- Never rely on Clay's own full-name dedup — do the real dedup pass in Claude using LinkedIn URL → Email → Full Name+Company Name, in that priority order.
- Prefer Claude over Clay for anything Claude can do just as well, on cost-efficiency grounds ($20/month vs $120–190+/month) — "use less Clay features as possible."
- Always default job-title search to "similar to," not "contains," in Clay's people search — contains silently loses up to ~60% of valid leads.
- Push qualification filtering upstream into the source data tool (Prospio/Apollo/Crossview) wherever that tool already offers the exact filter natively, rather than re-deriving it inside Clay.
- A realistic qualification pipeline should pass roughly 60–70% of a 100-company list; if your signals are dropping that to 20–30%, the parameters are too strict/vague — fix the logic rather than accept the loss.
- Don't fully trust Clay's own people database for final outreach-grade contact data — treat it as noisy (self-reported title claims) and cross-check.
- For non-English markets, always add the local-language term for core role keywords (e.g., "founder") in addition to English.
- Apply a minimum ~100 LinkedIn followers/connections filter on any outbound list to screen out low-activity/junk profiles.
- Set a "months in current role" minimum (Yogesh's default: 12; Gagan's counter-argument for informal buying processes: 6 is also fine) as a buying-authority proxy — the exact number is a strategy call informed by sales knowledge, not a fixed rule.
- In Sculptor, always keep the mode on "Analyze" — "Build" mode will start modifying your table, which is dangerous if you only meant to ask a question.
- Goal for the group this week: make the Clay table for the 50-company list "look perfect" — clean signals, no vague over-disqualification, valid LinkedIn/email on every included profile — because it will become the centerpiece of a portfolio video.
